# TWORLD

Личное PWA для трекинга тренировок, вредных привычек и дневника.
Django + DRF + PostgreSQL на бэкенде, React + Vite + TypeScript на фронте.

Приложение сделано вокруг одного принципа: **если ввод занимает больше
3 секунд или больше 2 тапов — он переделан**. Предыдущая версия провалилась
не из-за нехватки функций, а из-за того, что данные было неудобно вносить,
и человек начинал врать себе или бросал.

## Быстрый старт

### Вариант 1 — Docker (ничего не надо ставить)

```bash
cp .env.example .env
docker compose up --build
```

- фронтенд: http://localhost:5173
- API и документация: http://localhost:8000/api/docs/
- админка: http://localhost:8000/admin/

Демо-данные (90 дней истории) подгружаются отдельной командой:

```bash
docker compose exec backend python manage.py seed_demo
# вход: @demo_user / demo12345
```

### Вариант 2 — локально

Нужны Python 3.11+, Node 20+, PostgreSQL 14+.

```bash
# --- база ---
createuser tworld --createdb --pwprompt      # пароль: tworld
createdb -O tworld tworld

# --- бэкенд ---
python -m venv .venv && source .venv/bin/activate
pip install -r backend/requirements.txt
cp .env.example .env
python backend/manage.py migrate
python backend/manage.py seed_catalog        # справочники и библиотека упражнений
python backend/manage.py seed_demo           # демо-пользователь на 90 дней
python backend/manage.py runserver

# --- фронтенд (во втором терминале) ---
cd frontend
npm install
npm run dev
```

Открыть http://localhost:5173, войти как `demo_user` / `demo12345`.

В разработке фронтенд ходит по относительному `/api`, а Vite проксирует
запросы на бэкенд — CORS настраивать не нужно. Если бэкенд поднят
на другом порту:

```bash
VITE_DEV_API_PROXY=http://127.0.0.1:8001 npm run dev
```

### Проверка

```bash
cd backend && python -m pytest             # 69 тестов: изоляция данных, доменные правила, опрос, приглашения
cd frontend && npm run typecheck && npm run build
cd frontend && npm run e2e                 # сквозной прогон в Chromium под iPhone 14 Pro
cd frontend && npm run e2e:workout         # запись подхода, таймер отдыха, шаг по сетке зала
cd frontend && npm run e2e:screens         # все девять вкладок «Прогресса»

cd frontend && npm run e2e:onboarding      # регистрация нового пользователя и стартовый опрос

# Оффлайн-оболочка проверяется на собранном приложении: в разработке
# Service Worker намеренно отключён, чтобы не кэшировать правки.
cd frontend && npm run build && npm run preview &
cd frontend && npm run e2e:pwa
```

## Оформление — один файл

`frontend/src/styles/tokens.css` содержит **все** визуальные параметры:
цвета, шрифты, размеры, отступы, радиусы, тени, длительности анимаций,
тап-зоны, безопасные отступы iPhone и параметры стекла. Ни один компонент
не содержит хардкода — только `var(--…)`. Тёмная тема переопределяет
те же токены.

Семантические токены (`--color-warn`, `--color-ok`) намеренно спокойные:
предупреждение — янтарное, а не красное. Красный есть только у необратимого
действия — удаления аккаунта. Приложение не ругает пользователя цветом.

### Визуальный стиль

Светлый «воздушный» интерфейс: бледно-голубой фон с мягкими пятнами,
белые карточки с мягкой тенью и одним насыщенным синим акцентом.
За каждым типом данных закреплён свой тон — плитки иконок и полосы
прогресса берут его из `--tone-*`:

| Данные | Тон |
|---|---|
| вода | голубой `sky` |
| белок, настроение | зелёный `green` |
| добавки | жёлтый `yellow` |
| сон, вечер | фиолетовый `purple` |
| энергия, травмы | оранжевый `orange` |
| привычки | бирюзовый `teal` |

Общие элементы лежат в `shared/ui`:

- `primitives.tsx` — карточки, кнопки, сегментированный переключатель,
  кольцо прогресса, плитки иконок, строки меню, iOS-переключатель,
  шкала точками;
- `icons.tsx` — линейные SVG-иконки, встроенные в сборку (оффлайн-оболочка
  не зависит от шрифта иконок);
- `Keypad.tsx` — ввод числа своей клавиатурой в нижнем листе: вес
  записывается в два тапа, прошлое значение видно рядом с табло.

Профиль — меню, а не простыня настроек: каждая группа открывается в нижнем
листе. Действие экрана (настроить «Сегодня», настройки профиля) стоит
в шапке рядом с крупным заголовком — через `app/header.tsx`.

### Стекло

Размывают фон только те слои, под которыми реально едет контент: шапка,
таб-бар, нижние листы и таймер отдыха. Карточки плотные — белая плёнка
на 90% выглядит так же, а прокрутка не тратит кадры на десятки фильтров:
на экране одновременно 2 размывающих элемента. Механика лежит
в `styles/glass.css` и не содержит ни одного значения — только сборку
из токенов.

Стекло выключается тремя способами, и вёрстка это переживает — поверхности
просто становятся плотными:

| Способ | Где |
|---|---|
| Профиль → Внешний вид → Поверхности → «плотные» | пользователем, хранится локально |
| `prefers-reduced-transparency: reduce` | системная настройка iOS и macOS |
| `@supports not (backdrop-filter)` | браузеры без поддержки |

Проверки внешнего вида:

```bash
cd frontend && npm run e2e:appearance   # снимает области, меряет прокрутку
python scripts/contrast.py frontend/e2e/screenshots
```

`contrast.py` считает контраст **по фактическим пикселям**, а не по токенам:
сквозь плёнку просвечивает контент, и настоящий фон текста — это то, что
в итоге отрисовалось. Сейчас в карточках и шапке 16–17:1, в таб-баре
6:1 (светлая) и 8,6:1 (тёмная) при WCAG AA = 4.5:1.

## Решения, которые стоит знать до правок кода

**Длительности хранятся только в целых секундах.** В схеме нет ни одного
`TimeField` или `DurationField` для длительности упражнения. `85` — это
85 секунд, а не «час двадцать пять». Формат «1:15:37» невозможно ввести
физически: раньше именно он превращал 1 мин 15 сек в 1 час 15 минут
и ломал все агрегаты.

**Вес односторонних упражнений умножается на два.** У `SetLog` есть поле
`weight_is_per_side` — снимок флага упражнения на момент записи. Если
поменять флаг у упражнения задним числом, история не поедет.

**Сетка весов принадлежит паре «зал × упражнение».** `GymExerciseProfile.weight_steps`
хранит фактические значения тренажёра (`[36.2, 40.8, 45.3, 49.8, 54.4, 58.9]`),
кнопки +/− ходят по этому массиву. Один и тот же тренажёр в разных залах
даёт разные цифры.

**День выполнен, если закрыт блок `required`.** Статуса «тренировка провалена»
в схеме нет вообще. `main` и `optional` на зачёт не влияют.

**Пропуск по внешней причине не портит дисциплину.** Решает флаг
`FailReason.counts_against_discipline` на справочнике причин, а не код.
Пользователь может переопределить его в настройках.

**Срыв привычки не стирает историю.** Все три числа — «дней с решения»,
«текущая серия», «всего чистых дней» — вычисляются из событий, а не хранятся
счётчиками. Поэтому отметка задним числом пересчитывает их честно,
а «дней с решения» не обнуляется никогда.

**Основная цифра веса — тренд, а не сырое значение.** Скользящее среднее
за 7 дней пересчитывается при каждой записи. Разница между утренним
и вечерним весом доходит до 3 кг, и сырые цифры демотивируют зря.

**Калории выключены по умолчанию** (`UserSettings.track_calories = False`).
Пока выключено, в интерфейсе нет ни одного поля калорий — только белок.

**Запись данных переживает отсутствие сети.** `submitOrQueue()` сначала
пробует отправить запрос — тогда пользователь получает ответ сервера
(предупреждение о лимите веса, побитый рекорд). Если сети нет, запись
уходит в IndexedDB и отправляется позже; подход при этом сразу виден
в списке. Ошибки валидации в очередь не попадают: они не исправятся
сами, и прятать их за «синхронизируем потом» было бы враньём.

## Изоляция данных

Три слоя, а не один:

1. `OwnedModel` — обязательный `user` с каскадным удалением у всех
   пользовательских таблиц.
2. `OwnedModelViewSet.get_queryset()` всегда сужает выборку до `request.user`;
   владелец при создании берётся из запроса, поле `user` в теле игнорируется.
3. Тесты `backend/tests/test_isolation.py` проходят по реестру всех роутов
   и падают, если появится вьюсет без обязательной фильтрации. Плюс проверка
   «юзер Б получает 404 на объекты юзера А» по каждой модели.

Удаление аккаунта (`POST /api/accounts/delete/` с подтверждением ником)
удаляет все данные каскадом.

## Деплой

Пошаговая инструкция для закрытой беты — в [DEPLOY.md](./DEPLOY.md):
VPS, домен, одна команда запуска.

`docker-compose.prod.yml` поднимает всё сразу: Caddy с автоматическим
HTTPS от Let's Encrypt, собранный фронтенд, Django под gunicorn,
PostgreSQL без открытого порта и планировщик напоминаний. При старте
бэкенд сам применяет миграции, заливает справочники и собирает статику.

HTTPS обязателен: без него Service Worker не зарегистрируется, а значит
не будет ни оффлайна, ни установки на домашний экран, ни уведомлений.

PDF-отчёты требуют системных библиотек Pango и Cairo (в `backend/Dockerfile`
они уже стоят). Без них отчёт отдаётся печатаемым HTML — «Печать →
Сохранить как PDF» даёт тот же A4.

## Первый запуск для нового пользователя

После регистрации человек проходит стартовый опрос — шесть коротких
экранов, обязательна только цель. Ответы сразу превращаются в настройки
(`apps/accounts/onboarding.py`):

| Ответ | Что настраивается |
|---|---|
| цель, вес, желаемый вес | белок: 1,4–2,0 г на кг (при похудении — от веса ближе к целевому), вода: 33 мл на кг |
| место, опыт, дни, длительность | программа из библиотеки упражнений: до трёх дней — «всё тело» A/B по очереди, от четырёх — верх/низ; сразу в расписании |
| привычки | счётчики «без сладкого», «прогулки» и т. п. на главном экране |
| отбой, подъём, дорога | цель сна и «во сколько выйти из зала» |
| добавки | отметки одним тапом на главном экране |

Опрос можно пропустить целиком («Настрою сам») и пройти заново из профиля —
повторный проход не создаёт дублей.

## Закрытая бета

`REGISTRATION_INVITE_ONLY=True` — и зарегистрироваться можно только по коду.
Администратор создаёт коды в приложении (Профиль → «Пригласить тестеров»)
и отправляет ссылку вида `https://домен/?invite=ABCD-EFGH`: регистрация
откроется с подставленным кодом. Код бывает одноразовым или на группу,
его можно отозвать; видно, кто по какому коду пришёл. Из консоли:
`python manage.py invites create --count 10`.

## Уведомления

Не больше двух в день, каждое отключается отдельно, формулировок с укором нет.

```bash
python manage.py generate_vapid_keys      # один раз, ключи в .env
python manage.py send_notifications       # по cron каждые 5 минут
*/5 * * * * cd /path/to/backend && python manage.py send_notifications
```

Команда сама следит за лимитом, тихими часами и за тем, чтобы одно
уведомление не ушло дважды. `--dry-run` печатает, что было бы отправлено.

Ограничение iOS: web-push работает только для PWA, добавленной на домашний
экран, начиная с iOS 16.4. Без ключей VAPID приложение остаётся полностью
рабочим — просто без напоминаний.

## Apple Health

PWA не имеет прямого доступа к HealthKit — это ограничение iOS, а не проекта.
Поддерживаются два пути без нативного приложения, оба через
`POST /api/health/import/` (формат — в [docs/ai-exchange-format.md](docs/ai-exchange-format.md)):

1. **Apple Shortcuts → вебхук.** Автоматизация «каждое утро отправить сон,
   шаги и пульс покоя». Настраивается за пять минут, работает без App Store.
2. **Выгрузка `export.zip`** из приложения «Здоровье» — разовый импорт истории.

Повторная отправка тех же данных дублей не создаёт, а ручной ввод импорт
не перезаписывает: ручное значение всегда главнее.

## Интеграция с нейросетями

```bash
# весь контекст готовым markdown
curl -H "Authorization: Token twk_..." \
  "http://localhost:8000/api/context/?format=markdown"

# импорт плана обратно
curl -X POST -H "Authorization: Token twk_..." -H "Content-Type: application/json" \
  -d '{"text": "# Верх тела\n\n## Обязательный\n| Упражнение | Подходы | Повторы | Вес |\n|---|---|---|---|\n| Жим штанги лёжа | 4 | 6-8 | 62.5 |"}' \
  http://localhost:8000/api/plans/import/
```

Токены создаются в приложении: Профиль → Интеграции. Токен со скоупом
`read` физически не может изменить данные — это проверяется на сервере.

MCP-сервер (девять инструментов, включая `log_workout` и `create_plan`):

## Демо-данные

`python manage.py seed_demo --reset` создаёт пользователя `@demo_user`
с 90 днями истории. В данные намеренно заложены случаи, без которых
половину логики не проверить глазами:

- резкий скачок веса на жиме гантелей — и травма плеча следом;
- второй эпизод той же травмы внутри 60 дней (сработает предупреждение о рецидиве);
- трёхнедельный застой в тяге верхнего блока;
- неделя недосыпа с провалом самочувствия в зале;
- упражнение, пропущенное шесть раз подряд (сработает подсказка о порядке);
- срывы привычки с сохранённой историей;
- девять недель без разгрузки (сработает предложение деload).
