## 1.1 Стек: остаёмся на предложенном

Django + DRF + React/Vite + PostgreSQL — объективно хороший выбор под эту задачу, менять не предлагаю. Почему именно он тут уместен:

- Данные сильно реляционные (упражнение → подход → сессия → шаблон → зал → травма → лимит веса). Документная БД тут проиграет: почти каждый экран — это join и агрегат.
- Нужен серверный PDF (раздел 13) — у Python лучший в классе HTML→PDF (WeasyPrint) с полноценным CSS для печати.
- Нужны аналитика и корреляции (раздел 10) — pandas/numpy на бэкенде дешевле, чем считать это на клиенте.
- Нужен MCP-сервер (раздел 12) — официальный Python SDK, переиспользует те же модели и права доступа.

### Что добавляю к базовому стеку (и зачем)

| Компонент | Выбор | Обоснование |
|---|---|---|
| Язык фронта | TypeScript | Формат подхода (`секунды`, а не `время суток`) должен ломаться на этапе компиляции, а не в проде. Это прямая страховка от бага №3 из задания. |
| Серверный стейт | TanStack Query | Нужен кэш + оптимистичные апдейты + ретраи — основа оффлайна. |
| Локальная БД | Dexie (IndexedDB) | Оффлайн-очередь и чтение без сети. |
| Service Worker | vite-plugin-pwa (Workbox) | Манифест, прекэш, стратегии, обновления. |
| Графики | Recharts | SVG, работает оффлайн, стилизуется токенами; вертикальные линии событий (раздел 10) делаются штатным `ReferenceLine`. |
| Стили | **Чистый CSS + CSS-модули, без UI-китов и без Tailwind** | Tailwind — это уже дизайн-решение (своя шкала отступов, радиусов, цветов). По твоему требованию «не придумывай стиль» всё оформление живёт в одном файле токенов. |
| Примитивы | Radix UI (headless) | Доступность (фокус-трапы, ARIA) без единого пикселя чужого стиля. |
| PDF | WeasyPrint | HTML+CSS → A4, локальные шрифты, ч/б-читаемость. |
| Фоновые задачи | **не нужны** | PDF собирается за доли секунды прямо в запросе, импорт Health — тоже. Очередь понадобится только для расшифровки голосовых заметок, и добавить её можно будет тогда, а не заранее. |
| Документация API | drf-spectacular | OpenAPI 3.1 + Swagger UI. |

**Явно НЕ берём:** UI-киты с готовым визуалом (MUI, Chakra, Ant), Tailwind, Redux (избыточен), GraphQL (усложняет оффлайн-кэш без выгоды).

## 1.3 Изоляция данных — на уровне запросов

Требование раздела 1 («не только UI») реализуется тремя слоями, а не одним:

1. **Базовая модель.** Все пользовательские таблицы наследуют `OwnedModel` с `user = FK(settings.AUTH_USER_MODEL, on_delete=CASCADE)` и индексом по `(user, ...)`.
2. **Базовый вьюсет.** `OwnedViewSet.get_queryset()` **всегда** делает `.filter(user=self.request.user)` и `perform_create` проставляет `user` из запроса, игнорируя тело. Сериализаторы не принимают поле `user` вообще.
3. **Тест-страховка.** Автотест проходит по реестру всех роутов DRF и падает, если вьюсет не унаследован от `OwnedViewSet` и не помечен явно как публичный. Плюс параметрический тест «юзер Б получает 404 на все объекты юзера А» — по каждой модели, а не выборочно.

Дополнительно: `on_delete=CASCADE` от `User` вниз по всему графу → удаление аккаунта одной кнопкой действительно удаляет всё. Файлы (аватары, фото еды, фото прогресса, PDF) удаляются сигналом `post_delete`. Публичные ссылки на отчёты (`ShareLink`) отзываются каскадом.

## 1.4 Оффлайн: как это устроено

Зал и метро — основной сценарий, поэтому оффлайн не «деградация», а нормальный режим.

**Модель данных для синка.** Каждая таблица, в которую пишет пользователь, наследует `SyncableModel`:

| Поле | Назначение |
|---|---|
| `client_id` (UUID) | Генерируется на клиенте **до** отправки. `unique(user, client_id)`. Повторная отправка не создаёт дубль. |
| `updated_at` | Серверное время последнего изменения, курсор для `pull`. |
| `deleted_at` | Мягкое удаление — иначе удалённая оффлайн запись воскреснет при следующем pull. |
| `client_updated_at` | Время правки на устройстве — для разрешения конфликтов. |

**Протокол.**
- `GET /api/sync/pull?since=<ISO>` → все изменения пользователя после метки, постранично, включая тумбстоуны.
- `POST /api/sync/push` → массив операций `{op_id, entity, client_id, op, payload, client_updated_at}`. `op_id` уникален → повтор при обрыве связи безопасен. Ответ — карта `op_id → {status, server_state}`.
- Конфликт: **last-write-wins по полям** (не по записи), кроме «append-only» сущностей (подходы, попытки планки, логи тяги, срывы) — там конфликтов нет по определению, только объединение.

**Что кэшируется в IndexedDB:** сегодняшний день, активная тренировка, последние 90 дней метрик, библиотека упражнений, профили залов, быстрые продукты, привычки. Этого хватает, чтобы полностью провести тренировку без сети.

**Индикация.** Один ненавязчивый статус: «Синхронизировано» / «N изменений ждут сети». Без модалок и без блокировки ввода.

## 1.5 Таймеры, которые не врут

Три бага из задания (№2 и №3) — это баги хранения и жизненного цикла, поэтому решения архитектурные:

1. **Время всегда `PositiveIntegerField` в секундах.** В схеме БД нет ни одного `TimeField`/`DurationField` для длительности упражнения. `1:15:37` ввести физически некуда — поле принимает только целые секунды.
2. **Таймер считает не тиками, а по стенным часам.** Храним `started_at` (timestamp); отображение = `now - started_at`. Вкладка уснула, экран заблокирован, телефон в кармане — значение корректно после возврата.
3. **Секундомер статики не обнуляется записью.** Кнопка «Зафиксировать» создаёт **новую строку попытки** и продолжает счёт; сброс — только отдельным явным действием. Модель `SetLog` на каждую попытку, а не одно поле «результат».
4. **Защита от нуля.** Попытка короче 2 секунд не сохраняется молча, а показывает «Записать 1 сек?» с отменой. Это ровно тот случай «ткнул дважды → 0,44».
5. **Ручной ввод статики — в секундах**, с живой подсказкой под полем: `85 → 1:25`.

**Оговорка по iOS, которую надо знать заранее.** Веб-таймер не может разбудить заблокированный iPhone звуком сам по себе. Что реально работает в PWA: планируемое уведомление через Service Worker (Web Push, iOS 16.4+, только для установленной на экран «Домой» PWA) + вибрация/звук при возврате в приложение. Полностью надёжный «звонок при заблокированном экране» — это нативная обёртка (раздел 14, Live Activities). Предлагаю: PWA как основной путь, нативная обёртка Capacitor — отдельным этапом, схема БД её уже поддерживает.

## 1.6 Apple Health: честный план

PWA не имеет доступа к HealthKit — это ограничение iOS, не наше. Три пути, поддерживаем все три одним эндпоинтом `POST /api/health/import`:

| Путь | Что даёт | Сложность |
|---|---|---|
| **Apple Shortcuts → вебхук** (рекомендую как первый) | Автоматизация «каждое утро в 9:00 отправить сон/шаги/пульс». Работает без App Store, ставится за 5 минут. | низкая |
| Импорт `export.zip` из приложения «Здоровье» | Вся история разом, разово при старте. | средняя |
| Нативная обёртка (Capacitor + HealthKit-плагин) | Фоновая синхронизация, виджеты, Live Activities. | высокая |

Входные данные нормализуются в одну таблицу `HealthMetric` с `external_id` для дедупликации: повторная отправка тех же данных не создаёт дублей. Ручной ввод всегда помечается `source=manual` и имеет приоритет над импортом (раздел 6: «ручной ввод — только как правка»).

## 1.7 Аутентификация

- Регистрация по **email или телефону** + пароль (обязательно одно из двух, constraint на уровне БД).
- JWT: короткий access (15 мин) в памяти + refresh в `httpOnly; Secure; SameSite=Lax` cookie. Токен в памяти переживает оффлайн-сессию за счёт silent refresh при появлении сети; при полном оффлайне приложение работает на локальных данных и синкается после логина.
- Sign in with Apple — проверка `id_token` на бэкенде, привязка к существующему аккаунту по email.
- Сброс пароля — по email, одноразовая ссылка, 30 минут.
- **API-токены пользователя** (раздел 12) — отдельная сущность от сессионных JWT: хранится только хэш, скоуп `read` / `write`, показываются один раз, отзываются кнопкой.

## 1.8 Токены оформления

Единственный файл, который правится при подключении реального стиля: `frontend/src/styles/tokens.css`. Все остальные CSS используют только `var(--...)`, ни одного хардкода цвета/размера/шрифта. Состав:

```
--color-*      поверхности, текст, границы, акцент, семантика (ok/warn/info) — нейтральные серые заглушки
--font-*       семейства (system-ui как заглушка), размеры, высоты строк, насыщенности
--space-*      шкала отступов
--radius-*     радиусы
--shadow-*     тени
--z-*          слои
--duration-*   длительности анимаций
--tap-*        минимальные тап-зоны (44px по Apple HIG)
--safe-*       env(safe-area-inset-*)
```

Тёмная тема — переопределение тех же токенов внутри `@media (prefers-color-scheme: dark)`. Семантика в токенах присутствует (ok/warn), но **нейтральными оттенками серого**: подсветка «резкий скачок веса» будет заметной, но не «красной аварией» — это согласуется с принципом «никакого стыда».

## 1.9 Принципы, зашитые в архитектуру (а не в тексты интерфейса)

| Принцип из задания | Как гарантируется в коде |
|---|---|
| Ввод ≤ 3 сек / ≤ 2 тапа | В `docs/03-screens.md` у каждого поля прописан бюджет тапов; автосохранение по `onBlur`/дебаунсу, кнопки «Сохранить» нет нигде |
| Никакого стыда | Нет модели «штраф/провал». `WorkoutSession` не имеет статуса `failed`; пропуск — это `SessionExercise.status`, а не оценка дня. Дни болезни исключаются из статистики |
| Пропуск по внешней причине не портит дисциплину | `FailReason.counts_against_discipline` — флаг на справочнике причин, а не хардкод |
| Тренды вместо сырых цифр | Основная цифра веса — `trend_kg` (SMA-7), сырое значение отдаётся вторым полем |
| Один плохой день ничего не значит | Все агрегаты недельные; дневные значения показываются только на «Сегодня» |
